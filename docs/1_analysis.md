# РОЗДІЛ 1. АНАЛІЗ АНАЛОГІВ ТА ТЕХНІЧНЕ ЗАВДАННЯ

> Статус: заплановано (етап 1, 05.10.2026 – 31.10.2026).

# 1.2 Аналіз існуючих аналогів

Для порівняння обрано три програмні продукти: Jooble та Adzuna (прямі аналоги, агрегатори вакансій) і LinkedIn Jobs (опосередкований аналог, платформа з розподіленою інфраструктурою пошуку вакансій). Критерії порівняння обмежено технічними параметрами. Внутрішня архітектура Jooble та Adzuna публічно не розкривається, тому для цих систем аналіз ґрунтується на документації зовнішнього API [1]–[5]. Для LinkedIn Jobs використано інженерні публікації розробників платформи [6]–[10].

# 1.2.1 Jooble

Архітектурний патерн. Jooble функціонує як централізований агрегатор вакансій, що охоплює понад 60 країн. За зовнішнім інтерфейсом система є централізованим сховищем із пошуковим інтерфейсом, доступним клієнтам через синхронні запити. Така модель спрощує інтеграцію, проте покладає на споживача відповідальність за повноту й актуальність вибірки.

Протоколи передачі даних. Взаємодія реалізується через REST API: запит POST https://jooble.org/api/{api_key} із тілом JSON (keywords, location, salary, page, ResultOnPage, SearchMode). Відповідь містить totalCount та масив jobs (зокрема snippet, source, link). Недійсний ключ повертає код 403 [1].

Стек даних. Відомості про СУБД та механізми забезпечення консистентності не публікуються.

Технічні обмеження (Technical Bottlenecks). Доступ до даних реалізовано за запитами: механізми потокової доставки змін (change feed, webhook) відсутні, а повне охоплення потребує перебору пошукових запитів. Посилання у відповідях ведуть на ресурс Jooble [2]. Відповідь містить фрагмент опису (snippet) замість повного тексту вакансії. Передача ключа в шляху URL створює ризик його потрапляння до журналів проксі-серверів. Нормалізація та дедуплікація записів у документації не описані, тому виконуються споживачем самостійно.

# 1.2.2 Adzuna

Архітектурний патерн. Adzuna є агрегатором оголошень, що надає RESTful API з дев'ятьма ендпоінтами: пошук, категорії та чотири ендпоінти трендів (історія зарплат, гістограма зарплат, регіональні дані, топ роботодавців) [3]. API розділено за країнами (/jobs/{country}/search/{page}). Наявність готових агрегатів свідчить про попередньо обчислені аналітичні вітрини; внутрішня архітектура не розкривається.

Протоколи передачі даних. REST over HTTPS; формат відповіді: JSON (за замовчуванням), JSONP та XML (формат XML, згідно з документацією, не фіналізовано). Автентифікація виконується параметрами app_id та app_key у рядку запиту [3].

Стек даних. СУБД не розкривається. Ендпоінт гістограми повертає відповідність «нижня межа діапазону зарплат → кількість вакансій», порядок ключів не гарантується [4].

Технічні обмеження (Technical Bottlenecks). Для вакансій без вказаної зарплати застосовується прогноз (технологія Jobsworth); прогнозовані та заявлені значення змішуються у відповіді, тому споживач зобов'язаний перевіряти ознаку salary_is_predicted [5]. Модель доступу є pull; push-механізми у публічній документації не виявлено. Покриття кількох країн вимагає окремих запитів. Облікові дані у рядку запиту мають той самий ризик потрапляння до журналів, що й ключ у шляху URL.

# 1.2.3 LinkedIn Jobs

Архітектурний патерн. Пошук вакансій реалізовано як вертикаль на бібліотеках SeaS (Search as a Service) та Galene. SeaS відповідає за життєвий цикл сервісів і взаємодію вузлів кластера, Galene за низькорівневий інвертований індекс і живі оновлення [6]. Результати різних вертикалей об'єднуються у шарі Search Federation, що виконує розсилання запитів і змішування результатів [7]. Оновлення індексу виконується через nearline-конвеєр: трансформації на Apache Samza над потоками Apache Kafka [6]. Ізольовані вертикалі дозволили командам розвивати пошук незалежно, проте потребували високої експертизи та операційних зусиль, що спричинило створення керованої платформи Hosted Search [6].

Протоколи передачі даних. Apache Kafka використовується для потоків подій, Brooklin для передачі змін із баз даних [8]. У стеку інфраструктурних сервісів LinkedIn згадується Rest.li (власний REST-фреймворк компанії) [10].

Стек даних. Espresso є розподіленим відмовостійким документним сховищем і джерелом істини для багатьох застосунків [6]; модель консистентності Espresso описується як timeline consistency [9]. Додатково застосовуються Voldemort (key-value) та Galene (інвертований індекс). Базовий індекс Galene генерується офлайн раз на тиждень; live updater отримує зміни з Kafka та Brooklin і періодично поєднується зі знімком [8].

Технічні обмеження (Technical Bottlenecks). Підтримка кастомної вертикалі потребує високої пошукової експертизи [6]. Глобальний пошук по всіх партиціях таблиць Espresso тривалий час залишався незабезпеченою потребою інфраструктури [6]. Багаторівнева Search Federation потребувала консолідації кількох проміжних сервісів (міграція 2017 року), що є прикладом накопиченого технічного боргу [7]. Показники затримки (Latency) для пошуку вакансій публічно не розкриваються.

# 1.2.5 Аналітичний висновок

Аналіз показав, що Jooble та Adzuna надають доступ до агрегованих даних через синхронні запити REST із пагінацією, без публічно задокументованих механізмів доставки змін (change feed, webhook). Повне охоплення даних потребує перебору запитів, а споживач не контролює повноту, актуальність і правила дедуплікації. У Jooble ключ автентифікації передається в шляху URL, в Adzuna у рядку запиту, що збільшує ризик його потрапляння до журналів проксі-серверів. Adzuna змішує у відповідях заявлені та прогнозовані зарплати, що потребує додаткової фільтрації за ознакою salary_is_predicted. LinkedIn Jobs ілюструє вартість універсальних рішень: пошукові вертикалі на SeaS і Galene потребували значної експертизи та операційних зусиль, а відсутність глобального пошуку по партиціях Espresso тривалий час залишалася нерозв'язаною потребою інфраструктури.

Водночас LinkedIn демонструє ефективність nearline-конвеєрів: оновлення пошукового індексу відбувається майже в реальному часі через потоки Kafka, а базовий індекс періодично поєднується з потоком змін. Цей підхід адаптовано до масштабу кваліфікаційного проєкту: Ingestion Service публікує сирі вакансії до брокера повідомлень, Normalization & Dedup Worker споживає події асинхронно, PostgreSQL зберігає консолідовані записи, а Redis кешує результати аналітики за патерном Cache-Aside. Відокремлення збору від обробки усуває залежність затримки API від швидкості опитування джерел, а патерни Retry і Circuit Breaker (Resilience4j) ізолюють збої окремих джерел.

Обраний стек має компроміси: eventual consistency між подією збору та консолідованим записом, ускладнення операційної моделі (брокер, кеш, контейнеризація) та потребу в ідемпотентній обробці подій. Ці ризики компенсуються контрольованим масштабом системи та інструментальним контролем якості: Testcontainers, k6, SonarQube, Prometheus і Grafana. На відміну від проаналізованих аналогів, система забезпечує нормалізацію зарплатних вилок, дедуплікацію з вимірюваними precision, recall та F1 і відкриту модульну архітектуру підключення нових джерел. Проєктування архітектури, схеми даних та алгоритмів критичних вузлів розглядається в Розділі 2.
